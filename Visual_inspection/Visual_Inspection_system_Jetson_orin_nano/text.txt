# 2️⃣ Best method for *two 180° stitched views* (your case)

Since you **do not have a true 360 equirectangular frame**, the **correct and practical method** is:

## ⭐ **Two-Hemisphere Direction Mapping (Front/Back FOV Partitioning)**

### Core idea

* Treat **front 180°** and **back 180°** as **two independent panoramic sensors**
* Each has its own yaw range
* Convert detection center → **global yaw/pitch**
* Map yaw/pitch → pan–tilt angles

This avoids trying to “undo” Insta360’s internal stitching (which you *cannot* reliably do).

---

## 📐 Mapping logic (conceptual)

Let:

* Image size = `W × H`
* Top half = **front hemisphere**
* Bottom half = **back hemisphere**

### Step A — Determine hemisphere

```
if v < H/2 → FRONT hemisphere
else       → BACK hemisphere
```

### Step B — Compute local yaw (within 180°)

```
yaw_local = (u / W) * 180° − 90°
pitch     = 90° − (v_local / (H/2)) * 180°
```

### Step C — Convert to global yaw

```
if FRONT → yaw = yaw_local
if BACK  → yaw = yaw_local + 180°
```

Now you have a **single global yaw ∈ [−180°, +180°]**

👉 This is the **key insight** for your system.

# 4️⃣ Refinement using Logitech C920 (important)

Once pan–tilt moves to **rough direction**, you do **not need Insta360 accuracy anymore**.

## ⭐ **Image-based visual servoing (IBVS)**

### Logitech refinement loop:

1. Run YOLO on Logitech frame
2. Compute error from image center:

   ```
   ex = bbox_center_x − image_center_x
   ey = bbox_center_y − image_center_y
   ```
3. Apply small corrections:

   ```
   pan  += kx * ex
   tilt += ky * ey
   ```

This:

* Removes mapping errors
* Removes calibration dependency
* Is **standard robotics practice**

## 0) What you should *not* try (and why)

You should **not** try to recover “true Insta calibration” from that stitched webcam output.

## 1) Define the coordinate frames (so you don’t get lost)

You’ll have three coordinate spaces:

### A) Insta image coordinates

* Pixel center of detection: **(u, v)** in the stitched frame.

### B) Pan–tilt angles (actuators)

* **pan** angle: 0–180 (pin10)
* **tilt** angle: 20–160 (pin9)

### C) Logitech image coordinates

* Pixel center of detection: **(x, y)** in Logitech frame

Goal:

* Turn Insta detection into a **rough target pan/tilt**
* Then use Logitech detection to refine until the object is centered

## 2) Stage 1 — Coarse direction from Insta “two 180 views”

### What you have

A single stitched image of size **W × H**, where:

* **Top half** (v < H/2) = *Front 180°*
* **Bottom half** (v ≥ H/2) = *Back 180°*

This is basically a **front hemisphere view + back hemisphere view** in one frame.

### Step 1: Run YOLO on Insta frame

* You get bbox `(x1, y1, x2, y2)`
* Take bbox center:

  * `u = (x1+x2)/2`
  * `v = (y1+y2)/2`

### Step 2: Determine which hemisphere

* `front = (v < H/2)`
* `back  = (v ≥ H/2)`

### Step 3: Convert pixel → yaw/pitch (approximate but consistent)

Let `H2 = H/2`.

Normalize:

* `u_norm = u / W`
* `v_local = v` if front else `v - H2`
* `v_norm = v_local / H2`

Now map the 180° view:

* **yaw_half** (range −90°..+90°):

  * `yaw_half = u_norm * 180 - 90`
* **pitch** (range +90°..−90°):

  * `pitch = 90 - v_norm * 180`

Convert to a **global yaw**:

* If **front**: `yaw = yaw_half`
* If **back**:  `yaw = yaw_half + 180`

Wrap to (−180..+180] if you like:

* `yaw = ((yaw + 180) % 360) - 180`

✅ At this point you have a **rough direction** (yaw, pitch) without needing Insta intrinsics.

This idea matches how panoramic systems treat “panoramic direction” — you’re basically using a panorama-like mapping, but split into two hemispheres.

## 3) Stage 1.5 — Map yaw/pitch to servo angles (with your mechanical limits)

This is where your real-world “offsets” and constraints matter.

### A) One-time alignment constants (easy calibration)

You need two numbers:

* `yaw_offset`
* `pitch_offset`

How to get them (quick practical method):

1. Put a test object straight in front of the pan–tilt camera (Logitech).
2. Set pan=90, tilt=90.
3. Run YOLO on Insta and read the measured (yaw, pitch) for that object.
4. Define:

   * `yaw_offset = 90 - yaw_measured`
   * `pitch_offset = 90 - pitch_measured`

Now runtime:

* `pan_target  = yaw + yaw_offset`
* `tilt_target = pitch + pitch_offset`

### B) Apply mechanical clamping

* `pan_target  = clamp(pan_target, 0, 180)`
* `tilt_target = clamp(tilt_target, 20, 160)`  ✅ your safety requirement

### C) Smooth movement (interpolation)

You already implemented this:

* Move pan (pin10) smoothly first
* Then tilt (pin9) smoothly

This reduces power spikes and mechanical jerk.

## 4) Stage 2 — Logitech refinement using IBVS (the “research-grade” part)

Once you roughly point toward the object, you switch to **closed-loop control** using Logitech.

### What IBVS means (simple)

Instead of trusting geometry, you trust the **image error**:

* If object is left of center → pan a bit right
* If object is above center → tilt a bit up/down

This is the standard IBVS principle described by Chaumette & Hutchinson. ([Illinois Experts][1])

### Step 1: Run YOLO on Logitech frame

Get bbox center:

* `x = (x1+x2)/2`
* `y = (y1+y2)/2`

Image center:

* `cx = W_logi/2`
* `cy = H_logi/2`

Error:

* `ex = x - cx`
* `ey = y - cy`

### Step 2: Convert pixel error to angle correction

You have Logitech calibration (intrinsics `fx, fy`), so you can do this properly:

Small-angle approximation:

* `d_pan  ≈  atan(ex / fx)` (radians)
* `d_tilt ≈ -atan(ey / fy)` (radians)

Then convert to degrees and apply a gain:

* `pan += Kp_pan * degrees(d_pan)`
* `tilt += Kp_tilt * degrees(d_tilt)`

Why this is good:

* It’s more principled than “pan += kx*ex”
* It uses your known camera model
* It behaves consistently across resolutions / FOV

This is aligned with IBVS literature where error signals come from image features and camera parameters affect the interaction. ([Illinois Experts][1])

### Step 3: Clamp again (always)

* Pan: 0–180
* Tilt: 20–160

### Step 4: Iterate until centered

Stop when:

* `|ex| < threshold_px` and `|ey| < threshold_px`
  or when confidence drops.

This loop makes the system robust even if Stage 1 mapping is imperfect — that’s the whole advantage of IBVS.
